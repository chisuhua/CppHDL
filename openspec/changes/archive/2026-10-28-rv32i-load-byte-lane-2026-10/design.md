## 1. 机制读码结论

### 1.1 车道选择与扩展方式（`mem_stage.h:99-166`）

| `funct3` | 指令 | 车道选择 | 扩展 | 实现现状 |
|---|---|---|---|---|
| `000` | LB | `addr[1:0]` → byte0..3 | **符号** | ⚠️ **填充掩码错**（§1.2） |
| `001` | LH | `addr[1]` → half0/half1 | **符号** | ✅ 正确 |
| `010` | LW | 整字 | 无 | ✅ 正确 |
| `100` | LBU | `addr[1:0]` → byte0..3 | **零** | ✅ 正确 |
| `101` | LHU | `addr[1]` → half0/half1 | **零** | ✅ 正确 |

⚠️ **半字道按 `addr[1]` 选 ⇒ 半字对齐**（`addr[0]` 被忽略）⇒ 用例 MUST 用
**偶地址**（`0x100` / `0x102`）⇒ misaligned half 不在范围（Non-Goals）。
⚠️ **LH 的「✅ 正确」是指它当前的行为正确**（填充掩码 `0xFFFF0000` 恰好对），
但它**仍是手写掩码** ⇒ 与 LB **同型**的错误类别 ⇒ 本 change **一并**改成
`sext<32>`（**逐位等价**，见 §1.3）⇒ 一次消掉整类。

### 1.2 ⚠️ D1：LB 的符号扩展实现有 bug（实测）

`include/cpu/pipeline/stages/mem_stage.h:119-121`（**修前**）：

```cpp
auto byte_sign = bits<7, 7>(selected_byte);
ch_uint<32> lb_result = select(byte_sign,
    ch_uint<32>(4278190080_d) | zext<32>(selected_byte),  // 0xFFFFFF00   ← 注释与代码不符
    zext<32>(selected_byte));
```

- `4278190080 == 0xFF000000`，**不是**注释所写的 `0xFFFFFF00`；
- 字节符号扩展的正确填充是 `0xFFFFFF00`（把 bit7 复制到 bit31..8）；
- ⇒ `lb` 返回 `0xFF0000C3`，应为 `0xFFFFFFC3`；
- **同一模式的 LH 那行（`:140`，`4294901760 == 0xFFFF0000`）是正确的**
  ⇒ 这是**孤例**，不是「整套符号扩展都错」；
- ⚠️ 缺陷**从未被暴露**：LB/LBU/LH/LHU 在仓内的**唯一**用例是
  `test_riscv_tests*.cpp`，依赖**仓外** riscv-tests 二进制（`lb.bin`）
  ⇒ CI 中**全部 SKIP** ⇒ 有效覆盖为 **0**；
  `openspec/specs/rv32i-isa-semantics/spec.md` 此前也**完全没提** LB/符号扩展。

### 1.3 修法（**已实测验证**，非推断）

**首选**：换用框架已有的 `sext` 原语（`include/core/operators_width.h:109`），
**LB 与 LH 都换**：

```cpp
// LB（原 :119-121）
ch_uint<32> lb_result = select(byte_sign,
    sext<32>(selected_byte),
    zext<32>(selected_byte));

// LH（原 :139-141）
ch_uint<32> lh_result = select(half_sign,
    sext<32>(selected_half),
    zext<32>(selected_half));
```

理由：
- **三后端都支持** `sext`（interpreter `src/ast/ast_nodes.cpp:159`、
  JIT `src/jit/jit_ir_gen_lnode_logic.cpp:49` + `src/jit/jit_llvm_bit.cpp:76`、
  Verilog codegen `src/codegen_verilog.cpp:232/780/839`）
  ⇒ **不会**造成双后端语义分叉；
- Verilog codegen 发出 `{{24{<src>[7]}}, <src>}`（字节）/ `{{16{<src>[15]}}, <src>}`（半字）
  ⇒ 语义与 interpreter 一致；
- ⚠️ **消除错误类别**：本缺陷的成因正是**手写填充掩码 + 注释与代码不符**
  ⇒ 只修 LB 而把 LH 的**同型手写掩码**留在原地 ⇒ 「消除错误类别」只兑现一半
  ⇒ **LH 一并换 `sext`** 才真正消掉整类。

⚠️ **LH 的改动是逐位等价的（不是行为变化）**：
`sext<32>(x)`（x 为 16 位）= `x | (x[15] ? 0xFFFF0000 : 0)`
而原式 `select(half_sign, 0xFFFF0000 | zext<32>(x), zext<32>(x))`
= `x | (x[15] ? 0xFFFF0000 : 0)` ⇒ **完全相同**。
⇒ **既有 golden 零变化**（已实测：只改 LB 与同时改 LB+LH 两次跑本固件，
12 项写回序列**逐项相同**）。

**备选（最小改动）**：**只**把 LB 的常量改成 `ch_uint<32>(4294967040_d)`（= `0xFFFFFF00`）。
⇒ 若采纳备选，M5 的变异必须保留（否则缺陷形态无回归锁），
且 MUST 在本节写明「**LH 为何例外**」（否则与「消除错误类别」的理由不自洽）。

⚠️ `sext` 与 `zext` 的**静态断言**：`NewWidth >= ch_width_v<T>` ⇒ `32 >= 8` / `32 >= 16` ✓。

## 2. 固件设计（判别性固件，**独立**于既有 108 字固件）

⚠️ **独立** ⇒ 既有固件的 golden（24 项写回序列 / 停顿计数 / 退休数 178 /
`non_retired` 21）**零变化** ⇒ 「既有 golden 的变化 MUST 全部可归因」⇒ 本次归因 = **零**。
（⚠️ 该零变化已**实测**确认：带 §1.3 修复跑既有 dual 用例 ⇒
`10859 assertions in 5 test cases` 全绿。）

### 2.1 固件布局（20 字）

```
w0   ADDI x1, x0, 0xD4        ← 字节值 lane 0（bit7=1 ⇒ 对符号扩展有判别力）
w1   ADDI x2, x0, 0xC3        ← lane 1
w2   ADDI x3, x0, 0xB2        ← lane 2
w3   ADDI x4, x0, 0xA1        ← lane 3
w4   SB   x1, 0x100           ← 距离 4（w0）⇒ 走寄存器堆路径 ⇒ 不依赖前推
w5   SB   x2, 0x101           ← 距离 4（w1）
w6   SB   x3, 0x102           ← 距离 4（w2）
w7   SB   x4, 0x103           ← 距离 4（w3）
w8   NOP ×4                   ← w8..w11
w12  LB   x5, 0x100
w13  LB   x6, 0x101
w14  LBU  x7, 0x102
w15  LBU  x8, 0x103
w16  LH   x9, 0x100
w17  LH   x10, 0x102
w18  LHU  x11, 0x100
w19  LHU  x12, 0x102
```

⚠️ **造字 MUST 用 `SB`**（D2 的更正）⇒ `[0x100]` = `0xA1B2C3D4`：
- 4 个字节**各不相同** ⇒ 任一车道选错都立刻暴露；
- 4 个字节的 **bit7 全部为 1** ⇒ 符号扩展与零扩展**结果不同**（判别力前提）；
- `SB` 的源数据**低位对齐**、由总线按 `addr[1:0]` 选车道（`rv32i_pipeline.h:458-467`）
  ⇒ `SB x2, 0x101` ⇒ lane 1 = `0xC3` ✓；
- `DataTCM` 的写是**读-改-写**（`rv32i_tcm.h:102-117`）⇒ 4 次 `SB` 依次合并进同一个字。

⚠️ **依赖距离**：4 条 `SB` 各自与自己的 `ADDI` 相距 **4**（中间隔 3 条无关指令）
⇒ 走**寄存器堆路径**（ADR-047 D11 的组合旁路修的是**距离 3**）
⇒ 不把「前推」混进本用例的判别里。
⚠️ 8 条 load **连续**（w12..w19）且**写互不相干的 `rd`** ⇒ 无数据依赖 ⇒ 无 load-use 停顿
⇒ 本用例**不**测停顿（停顿由既有固件与 ADR-047/048 的用例覆盖）。

### 2.2 ⚠️ D2：为什么 `SW` 造不出这个字（机制）

初稿用 `SW x1, 0x100` / `SW x2, 0x101` / … 期望拼出 `0xA1B2C3D4`。**不成立**：

| 环节 | 代码 | 后果 |
|---|---|---|
| `SW` 的字节使能 | `mem_stage.h:195`：`sw_be = 0xF` | **整字**，不是字节道 |
| `SW` 的数据对齐 | `rv32i_pipeline.h:460-461`：`store_is_partial = is_store & (funct3 != 010)` | `SW`（funct3=010）⇒ **不移位** |
| `DataTCM` 的合并 | `rv32i_tcm.h:114-116`：掩码 `0xFFFFFFFF` ⇒ 整字覆盖 | 前一次写**被完全覆盖** |

⇒ 实测：4 次 `SW` 后 `[0x100]` = `0x000000A1`（**最后一个**写胜出），
且 4 个车道 = `0xA1 / 0x00 / 0x00 / 0x00` ⇒ **3 个车道相同** ⇒ 判别力前提被破坏。
⚠️ **2026-10-28 订正**：初稿此处写的是 `0xA1 / 0x00 / 0x00 / 0xA1` —— **错**。
根因：`SW` 的字节使能是 `0xF`（**整字**）⇒ `DataTCM` 的合并掩码是 `0xFFFFFFFF`
⇒ **末次写整字覆盖**前一次 ⇒ 整字只剩**最后一个**值 `0x000000A1`
⇒ lane1/lane2/lane3 **全是** `0x00`（**不是** lane3 = `0xA1`）。
（该错误连带推翻了初稿「M7 下 #7 不红」的预测 ⇒ 见 §4 的订正。）
（⚠️ 仓库**既有**固件也印证这一点：既有用例做部分写用的是 `SB`/`SH`
（`SB(2,0,0x101)` ⇒ 字 = `0x030A`），**从不用 `SW` 写到字节偏移**。）

⚠️ **逐项的判别力画像**（供实施者判断判别力边界，勿误判）：

  （它只能区分「恒取 lane0」与「恒取 lane1」这类**整体错位**）
  ⇒ 对**扩展方式**（M2）与**填充掩码**（M5）有判别力；
- **#7**（`LBU@0x103`）读 lane3 ⇒ 对「车道选择」有判别力（lane3 = `0xA1` ≠ lane0 = `0xD4`）
  ⚠️ **2026-10-28 实测订正**：初稿称「对 M7 **零判别力**（`SW` 造字下 lane3 恰为 `0xA1`
  = 期望值 ⇒ 不红）」—— **该预测是错的**：`SW` 造字下整字 = `0x000000A1`

- **#10**（`LHU@0x100`）读的是**基线半字** ⇒ 对「half 选择」维度**零判别力**
  （能区分它的只有 half **取反**）⇒ 对**扩展方式**无判别力（`LHU` 本就零扩展）；
- 其余 9 项各自含**非零 offset**（#5/#6 = lane1/lane2；#8 = half0@0x100；
  #9/#11 = half1@0x102）⇒ 对「车道/半字选择」有判别力。

## 3. 断言设计

1. **写回序列**（最强）：12 项**逐项**比对（**不去重** —— 任何连续重复都是真回归）；
2. **每条 load 的值**：由写回序列承载（`x5..x12`）；
3. **反向期望**：上表逐条给出（`X_old != X_new`）；
4. **双后端逐拍全等**（27 个顶层输出，**无掩码**）—— 既有 dual 用例已有该机制，
   新固件 MUST **另起**一个 TEST_CASE（独立固件 ⇒ 既有 golden 不动）。
