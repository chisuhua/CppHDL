# Design: input-port-driving-guard-2026-10（可行性 spike）

> 本 change **只出文档**（无代码改动）⇒ 交付物 = 本文件。
> ⚠️ 目标：「**新增**输入端口 MUST 被显式驱动」的**自动化**。
> ⇒ 本 spike 的产出是**决策门结论**（实施 / 关闭）+ 候选对比 + **实测证据**。

## 0. 决策门结论

⇒ **通用状态型护栏**（判据：「所有**从未被驱动**的顶层输入端口都报」）**关闭**
—— 两条**互相独立**、且**都不依赖**有 bug 的那份测量的理由：
① **运行期方案的诊断不可行动**：运行期**无法识别端口身份**（§3.1，**实测**）
   ⇒ 最多只能说「这个 DUT 有 3 个未驱动输入（宽度 32/1/4）」⇒ 开发者仍不知道该驱动哪个；
② **语义判定缺承重件**：「从未被驱动」≠「应该被驱动」⇒ 需要「必需端口注册表」
   —— 而规范层**已明文**要求它（`openspec/specs/rv32i-isa-semantics/spec.md:60-87`）。
⇒ ⇒ 另有一条**结构性**论证（§3.2.1）：per-TEST-CASE 粒度是**必需的**
（文件粒度会掩盖），而平规则在该粒度上**必然**误报（只跑写路径的用例**理应**
不驱动读通道）⇒ ⇒ 「在必需的粒度上误报，在不误报的粒度上无效」⇒ **死结**。

⇒ ⇒ **推荐替代 = 「事件驱动（git diff）增量检查」**：只针对**本次变更新增的
`ch_in` 端口**列出「新增端口 + 全部实例化点」⇒ **半自动 + 人工确认**
⇒ 实测负载 **≈0–2 个新端口/commit**（§3.4）⇒ 成本趋零、误报趋零
⇒ ⇒ **建议实施**（**另一个** change；本 spike 不实施）。

⇒ ⇒ 义务**同时**留在 `AGENTS.md §ANTI-PATTERNS`（人工核对 + code review）
⇒ ⇒ 并**独立立项**「**必需端口注册表**」（规范层已承认需要，见 §3.3）。

## 1. 需要解析什么（C++ 表达式 → 端口集合）

要让护栏判「某组件的某 `ch_in` 端口是否被驱动」，需要**两个集合**：

| 集合 | 含义 | 难点 |
|---|---|---|
| **A：应该被驱动** | 该 DUT 的哪些输入端口**该**由 TB 驱动 | ① 端口**身份**（哪个端口）；② 「该」——**读值风险**逐端口不同 |
| **B：实际被驱动** | 测试里驱动了哪些 | ① C++ 表达式任意（`dev.instance().io().x` / `io.x` / `io().x` / helper / 宏 lambda）；② **内部驱动**（`io().x <<= y`）**不是** TB 驱动 |

### 1.1 集合 A 的「身份」问题 —— 框架侧**已有**现成定义

`src/codegen_verilog.cpp:350-357`（Verilog 顶层端口过滤）：

```cpp
if (port_node->type() == ch::core::lnodetype::type_input) {
    auto *in = static_cast<ch::core::inputimpl *>(port_node);
    if (in->driver() == nullptr) {      // ← 无内部驱动 ⇒ 顶层端口 ⇒ TB 的事
        filtered_ports.push_back(port_node);
    }
}
```

⇒ ⇒ **「顶层输入端口」= `type_input && driver() == nullptr`** —— 这是框架**已发布**的语义
（Verilog 顶层端口集 / JIT 的 `jit_ir_gen_lnode_io.cpp:31-46` 与之同构）
⇒ ⇒ 集合 A 的**成员判定在运行期完全可做**（`ctx->get_nodes()` + `driver()`）。

### 1.2 集合 A 的「该」问题 —— **逐端口的风险不同**（无法用一条平规则）

`openspec/specs/rv32i-isa-semantics/spec.md:60-87`（规范层已承认）：

> - `DataTCM.strbe` MUST 被其实例化点显式驱动
> - ⚠️ 范围限定：「任意新增输入端口 ⇒ 全实例化点 MUST 显式驱动」是**框架层约定**，
>   其核验需要一个「**必需端口注册表**」…… ⇒ **独立立项**
> - 不同端口的未驱动读值语义不同（`rst_n` 读 0 = 永久复位；`strbe` 读全 1 = 碰巧整字写）

⇒ ⇒ 「所有未驱动端口都报」**在语义上就是错的**：一个只跑写路径的测试**理应**
不驱动读地址端口（§3.2 的实测正是这个形态）。

## 2. 候选设计对比

| # | 设计 | 成本 | 误报面 | 可测性 | 结论 |
|---|---|---|---|---|---|
| **A** | **显式登记表**（「组件 → 必须驱动的端口列表」+ grep 检查） | **低**（一个清单文件 + grep） | **低**（只覆盖登记项） | **高**（`verify_rst_n_wiring.sh` 已是可用的原型） | ⭐ **登记表是**所有**方案的共同前置**（§1.2）⇒ 不是「替代方案」，是**承重件** |

## 3. 实测证据（4 条，全部可复现）

### 3.1 运行期**无法识别端口身份** ⇒ 候选 C 的诊断**不可行动**

独立探针（`/tmp/opencode/probe_ports.cpp` + `probe_v.cpp`，链接 `build/libcpphdl.a`）
对 `AxiLiteGpio` / `AxiLiteTimer` / `AxiLiteI2c` / `AxiLiteSlave` / `HazardUnit` 实测：

| 身份来源 | 实测值 | 可用？ |
|---|---|---|
| 运行期节点名（`inputimpl::name()`） | **全部** = `dut.unnamed_input` | ❌ 全部端口**同名** |
| 运行期 `source_location`（`lnodeimpl::sloc()`） | **全部** = `include/core/io.h:219` | ❌ 那是 `port()` 默认构造点（`io.h:219`），**不是**成员声明行 |
| 生成的 Verilog 顶层端口名 | `dut_unnamed_input` / `_1` / `_2` … `_12` | ❌ **位置化**，无语义 |

**根因**：端口成员**全部未显式命名**（`include/` 里 **641** 个 `ch_in<...>` 声明，
**0** 个带 `{"name"}` 初始化）⇒ `ch_logic_in` 用默认构造 ⇒ 名字退化、
`source_location` 落在**端口类的默认构造点**而非**成员声明点**
（C++ 无法从默认构造反推成员声明位置，除非改成默认成员初始化器或宏）。

⇒ ⇒ **后果**：运行期检查最多只能说「这个 DUT 有 3 个未驱动输入（宽度 32/1/4）」
⇒ **开发者仍不知道该驱动哪个** ⇒ ⇒ **候选 C 必须先解决「端口身份」**
⇒ 而那意味着 **641 处声明改造 + Verilog 端口名改变**（⇒ Verilator 缓存 key 变
⇒ golden file 变）⇒ ⇒ **需要 ADR + 全库级机械改动** ⇒ 成本 ≫ 收益 ⇒ ❌ **关闭**。

> ⚠️ 补充：`__io(...)` 宏（`include/core/io.h:312-319`，仓内 **267** 次使用）
> **是宏** ⇒ 理论上可携带 `__FILE__`/`__LINE__` ⇒ 但当前形态是
> 「一个宏调用里放一整串声明」⇒ 要逐成员携带位置 ⇒ **需改调用形态**（267 处）
> **+** 把另外 **374** 处裸声明也迁过去 ⇒ 同样是全库级改动。

### 3.2 平规则「所有未驱动端口都报」：**在必需的粒度上误报，在不误报的粒度上无效**

> ⚠️ **本节初稿的测量表已被自查推翻并作废**（根因见 §3.2.3）⇒ 保留订正痕迹。

#### 3.2.1 两个粒度，两个结论

| 粒度 | 实测 / 论证 | 结论 |
|---|---|---|
| **文件闭包**（测试文件 + 其递归包含的本地 fixture 头） | **实测** 4/4 个代表性 DUT 的未驱动端口 = **0**（`AxiLiteGpio` 13/13、`AxiLiteTimer` 12/12、`AxiLiteUart` 13/13、`AxiLiteI2c` 14/14） | 平规则在这个粒度上**零误报** ⇒ 它**不是**问题 |
| **per-TEST-CASE** | **结构性论证**（非测量）：一个**只跑写路径**的用例**理应**不驱动读通道（`araddr` / `arprot` / `arvalid` / `rready`）⇒ 平规则在此粒度**必然**误报 | ⇒ **per-case 粒度不可用** |

#### 3.2.2 为什么 per-case 粒度是**必需**的（⇒ ⇒ **死结**）

现有护栏的头注释已给出理由（`scripts/verify_rst_n_wiring.sh:11-15`）：

> 「Granularity matters: file level is not enough, because a file that drives
> rst_n for one DUT would mask another DUT in the same file.」

⇒ ⇒ **文件粒度会掩盖** ⇒ ⇒ 所以 per-case 是必需的
⇒ ⇒ ⇒ **平规则：在必需的粒度上误报，在不误报的粒度上无效** ⇒ ⇒ **死结**。

⇒ ⇒ 现有护栏能成立，是因为它只查 **`rst_n` 这一个「必需端口」**
⇒ ⇒ 一旦推广到「所有端口」，per-case 粒度的误报立刻出现
⇒ ⇒ ⇒ 平规则**必须**先有「哪些端口是**必需**的」这层判定（§1.2）
⇒ ⇒ ⇒ **登记表（候选 A）是承重件**。

#### 3.2.3 ⚠️ 初稿测量表被**自查**推翻（保留痕迹，避免后人重走）

初稿的表（4 行 DUT 的「未驱动端口」计数）**作废**。根因 = **测量脚本的正则 bug**：
捕获第一个实参时用了 `[^,;)]+` ⇒ 该字符类**排除了 `)`** ⇒ 对
`sim.set_input_value(dev.io().awvalid, v)` 这种**最常见**的 `io().X` 形态
只能匹配到 `io` ⇒ ⇒ 端口名**全部错位** ⇒ 「已驱动」被严重低估 ⇒ ⇒ 整表作废。

⇒ ⇒ 连带被推翻的还有**归因**：GPIO/Timer/Uart 的 `araddr`/`arprot` 实际由
**跨文件 fixture helper**（`tests/axi_lite_slave_fixture.h:96-97` 的 `read_io()`）驱动
⇒ ⇒ 初稿说的「该测试只跑写路径 ⇒ 读地址端口理应不驱动」**不是**那些用例的情况。

⇒ ⇒ ⇒ **平规则被关闭的理由因此改为两条更强、且与那份有 bug 的测量无关的**：
① **运行期端口身份不可得 ⇒ 诊断不可行动**（§3.1，**实测**）；
② **「从未被驱动」≠「应该被驱动」** ⇒ 缺承重件（「必需端口注册表」），
且规范层**已明文**要求（`openspec/specs/rv32i-isa-semantics/spec.md:60-87`）。
⇒ ⇒ ⇒ 而 per-case 粒度的误报（§3.2.1）现在是**结构性论证**，不依赖任何测量。

### 3.3 驱动**藏在 helper / 宏**里 ⇒ 静态分析**必须**做过程间分析

全仓普查（`tests/` + `examples/` + `samples/`，**271** 个源文件）：

| 量 | 计数 | **口径**（可复核） |
|---|---|---|
| 扫描面 | **271** 个源文件 | `tests/` + `examples/` + `samples/`，扩展名 `.cpp/.h/.hpp`，排除 `catch_amalgamated.*` |
| `set_input_value(` 出现（**含注释**） | **2557** | 两路独立普查**逐字一致** ⇒ 实现无关 |
| `set_input_value(` 出现（剥注释后） | **2542** | ⚠️ 另一路普查得 2496 ⇒ 差异**只来自注释剥离实现**（字符串字面量里的 `//` 是否被剥离）⇒ 故正文以**含注释的 2557** 为准（实现无关），剥注释数仅作参考 |
| 含 ≥1 次调用的文件 | **102 / 271** | 剥注释后 |
| `TEST_CASE(` 调用 | **1143** | ⚠️ **不承重** ⇒ 两路独立普查得 1143 / 1171（**口径差异**）⇒ 引用时 MUST 附命令；本仓 `TEST_CASE_METHOD` / `TEMPLATE_TEST_CASE` / `SCENARIO` 的调用数**实测均为 0** |
| **文件作用域 helper**（函数体含驱动） | **29 个函数 / 213 处调用 / 15 个文件** | ⚠️ **严格定义** = 顶格定义的具名函数；放宽到「任何作用域的函数」会得 123 个（把 `main` 与宏体也算进去）⇒ **口径不同，不是矛盾** |
| `DUAL_BACKEND_TEST_PAIR` 调用 | **186** 次（其中 **133** 次驱动在 lambda 体内） | 两路一致 ✓ |
| **驱动 100% 藏在 helper 里**的文件 | **6** 个 | — |
| `io().X <<= Y`（**内部**驱动，非 TB 驱动） | **682** 处（其中落在 `ch_in` 上的 **187** 处 ⇒ wrapper / 父组件接线 ⇒ **不是缺陷**） | 方向解析需 DUT 头类型表 ⇒ **187** 这一子计数由人工核实类型得出 |
| `io().X = value` 落在 `ch_in` 上（`CHERROR` + 端口保持未驱动 ⇒ **真缺陷**） | **10** 处（`examples/` 4 + `samples/` 6，**`tests/` 0**） | ⚠️ **无法用正则区分 `ch_in` / `ch_out`**（`io().rdata = ...` 落在 `ch_out` 上是**合法**的）⇒ 须**解析 DUT 的 `io_type`** ⇒ ⇒ **这本身就是「静态方案需要一个 DUT 头类型解析器」的证据**（§2 候选 B 的成本来源） |

⇒ ⇒ **只扫 `TEST_CASE` 体内的 `set_input_value` 会把这 15+6 个文件全部误报**
⇒ ⇒ 现有 `verify_rst_n_wiring.sh` 的 `calls_driver()` 已是可复用原型，
但它是**纯文本启发**（**不查实参** ⇒ 同一 helper 驱动 DUT-A / DUT-B 时互相掩盖）。

⇒ ⇒ **「有意不驱动」目前只有 1 个机器可识别的先例**：
`tests/test_axi_rst_n_guard.cpp`（标记 `rst_n_guard: intentionally-unwired`）
⇒ ⇒ 「必需端口注册表」还需要一个**通用的豁免机制**（当前只有 `rst_n` 一个特例）。

⇒ ⇒ ★ **顺手发现的 10 处真缺陷**（`io().X = value` 落在 `ch_in` 上 ⇒ 静默失效）：
`examples/spinalhdl-ported/uart/uart_tx.cpp:193,194,203,205` ·
`samples/stream_component_example.cpp:78,79,80,119` ·
`samples/stream_handshake_example.cpp:92,131`
（⚠️ 这 10 处是**人工核实端口方向**后得出的 ⇒ **自动检出需要 DUT 头类型解析器**
⇒ ⇒ 见 §2 候选 B 的成本；⇒ 也说明候选 E（半自动 + 人工确认）**不会**漏掉它们）
⇒ ⇒ **这 10 处正是「新输入端口 MUST 显式驱动」要抓的东西** ⇒ 但它们**不在 `tests/`**
⇒ ⇒ 现有 `verify_rst_n_wiring.sh` **不覆盖**（它只查 `rst_n`，且不查 `=` 形态）
⇒ ⇒ **独立立项**（可直接修，**不需要**通用护栏）。

### 3.4 事件驱动方案（候选 E）的负载实测：**≈0–2 个新端口/commit**

方法：`git log -100` ⇒ 逐 commit 统计 `include/` 下**新增行**里匹配
`ch_in<...> name;` 的数量：

| 新增 `ch_in` 数 | commit 数 |
|---|---|
| 0 | **92** |
| 1 | 5 |
| 2 | 1 |
| 4 | 1 |
| **85** | 1（`e015c027` = ADR-046 的**一次性单源化重构** ⇒ 结构性 outlier） |

⇒ ⇒ 典型增量负载 = **0–2** ⇒ ⇒ 一次 PR 的「新增端口 + 其全部实例化点」
⇒ **人工确认成本 ≈ 0** ⇒ ⇒ 候选 E 的成本/误报比**远优于**所有状态型方案。

## 4. 推荐方案 + 为什么不是另外几个

### 4.1 推荐：**候选 E（事件驱动增量检查）** + **候选 A（必需端口注册表）**（分两个 change）

| 维度 | 理由 |
|---|---|
| **误报面** | 只看**本次新增**的端口 ⇒ 范围 = 0–2 个 ⇒ 误报趋零 |
| **成本** | 行级 git diff + 正则 + grep ⇒ **无新依赖**、**无框架改动**、**无 ADR** |
| **覆盖的正是真实痛点** | 痛点是「**新增**端口忘了驱动」⇒ 事件驱动**正好对准** |
| **与既有护栏互补** | `verify_rst_n_wiring.sh` 守「**存量**的 `rst_n`」⇒ E 守「**新增**的任何端口」 |
| **可测性** | 纯 git + grep ⇒ 可用 fixture 自测（与 `verify_example_test_wiring.sh` 同型） |

### 4.2 为什么**不是**候选 C（运行期）

**两条独立的杀手**（任一即足以否决）：

1. **诊断不可行动**（§3.1，**实测**）：端口身份三重退化（节点名 / `source_location` /
   Verilog 名）⇒ 最多只能说「这个 DUT 有 N 个未驱动输入（宽度 …）」⇒ 开发者仍不知道
   该驱动哪个 ⇒ ⇒ 修复它需要 **641 处声明改造**（+ Verilog 端口名变 ⇒ Verilator 缓存
   key 变 ⇒ golden file 变）⇒ **ADR + 全库级机械改动** ⇒ 成本 ≫ 收益；
2. **语义判定缺承重件**：「从未被驱动」≠「应该被驱动」⇒ 即便身份修好，
   仍需要「哪些端口**必需**」这层判定 ⇒ 规范层**已明文**要求「必需端口注册表」
   ⇒ ⇒ 而该登记表**与运行期无关**（静态即可）⇒ ⇒ ⇒ 候选 C 的**框架成本
   买不到它需要的那层判定**。

⇒ **附：一条「读追踪」变体也不改变结论** —— 「只报『值被消费但从未被驱动』的端口」
（即只报 `get_users()` 非空的）⇒ 仍是**运行期**方案 ⇒ 同样受制于「身份不可得」
⇒ 且它**只**解决了「DUT 用不用它」，**没**解决「该驱动吗」⇒ ⇒ 结论不变。

### 4.3 为什么**不是**候选 B（clang 解析）

- 目标是「自动化**所有**端口的驱动检查」⇒ 而 §3.2 实测**平规则本身就是错的**
  ⇒ 解析再准也只能得到一个**语义错误**的结论；
- 依赖成本高（新增 clang 依赖 + 解析器自身的坑）；
- ⇒ 但 B 的**过程间分析能力**在候选 E 里**仍然有用**（判定 helper 内的驱动）
  ⇒ ⇒ **若**将来要自动化**存量**端口，B 才是正解 ⇒ ⇒ 属**后续**独立立项。

### 4.4 为什么**不是**「只做候选 A（登记表）」

- 登记表只覆盖**人工登记**的端口 ⇒ **新端口不会自动进表** ⇒ 恰好漏掉本 change 的目标；
- ⇒ ⇒ A 与 E **互补**：A 守「已知的必需端口」（存量、逐端口风险分级），
  E 守「新增端口」（自动发现）。
- ⚠️ 另：A 的「登记表 ⊆ 实际端口」交叉校验**只能查出过时条目**，
  **查不出**「新增端口未登记」⇒ ⇒ 「新端口必须登记」这条义务**不能**由 A 承担
  （否则就把「所有端口都必需」的平规则又请回来了）⇒ ⇒ **必须**由 E 承担
  ⇒ ⇒ ⇒ 这就是 A 与 E **必须并存**、**不能合并**的原因。
