# 提案：「新增输入端口 MUST 被显式驱动」自动化 —— **先做可行性 spike**

- **架构依据**：无（spike 只出文档）
- **5 段草案**：`.rddf/improvements/input-port-driving-guard-2026-10.md`
- **roadmap 归属**：工程纪律项
- **规格影响**：**无** ⇒ 归档用 `--skip-specs`
- **规模 / 风险**：**低**（只读）—— 价值在于**避免**开写一个高误报护栏

## Why

未驱动的输入端口读到的是**未定义值**（实测：`strbe` 读**全 1**、`rst_n` 读 0）
⇒ 依赖默认值的测试会「**碰巧**通过」而跨后端行为可能分叉。

⚠️ **反复指向**（2026-10-27 两轮审稿）：
- Batch 2/3 第 1 轮 BLOCKER = 「第 1 拍前只驱动了 6/7 个输入端口」；
- M3' 实测**零判别力**（删掉那行驱动仍全绿）⇒ 如实记录「**未驱动端口没有通用的
  变异判别力**」；
- 根 `AGENTS.md §ANTI-PATTERNS` 登记：「⚠️ 当前**无自动化护栏**覆盖这一类
  （`scripts/verify_rst_n_wiring.sh` 只覆盖 `rst_n`）」。

⚠️ **但静态分析这一类护栏有明确前车之鉴**：
`scripts/verify_example_assertion_quality.sh` 的**自研 C 子集分析器**
「**不可能被完全闭合**」⇒ 对抗审稿第 4/5/6 轮的**全部** BLOCKER 都出在它身上
⇒ **误报**是这类护栏的主要失败模式 ⇒ 直接开写护栏的风险很高。

## What Changes

（**spike：只出文档，不改实现**）

- **需要解析什么**：从 C++ 测试源码判定「某组件的某个 `ch_in` 端口是否被驱动」
  ⇒ 表达式解析（`sim.set_input_value(dev.instance().io().x, …)` / `io().x <<= …` /
  fixture 里的统一驱动 helper）⇒ **C++ 表达式的任意性是核心难点**；
- **候选设计**（各自评估成本 / 误报面 / 可测性）：
  1. **显式登记表**：仓库内维护「组件 → 必须驱动的端口列表」+ grep 式检查
     （成本最低、误报最低，但**登记表本身可能过时** ⇒ 需要「登记表 ⊆ 组件实际端口」的
     交叉校验）；
  2. **C++ 解析**（clang-based / libclang）：最准，但引入新依赖 + 解析器自身的坑；
  3. **运行期检查**：在 `Simulator` 侧记录「本 context 内被驱动过的输入端口」，
     在 `tick()` 时报告**从未被驱动**的输入端口 ⇒ **零解析成本**、
     但 ⚠️ **「零误报」是未经实测的断言**（见下）⇒ 需要**框架层加 API**
     ⇒ 触及公共 API 面 ⇒ 需 ADR；
     ⚠️ **实测（2026-10-28）**：框架**当前没有**「输入端口被 TB 驱动过」的追踪
     —— `Simulator::set_input_value()` 只写 `data_map_`（`include/simulator.h:417`）
     —— `inputimpl::set_driver()` 记的是**组件内部**驱动（`io().x <<= y`），
     **不是** TB 驱动 ⇒ 候选 3 确实需要**新框架 API** ⇒ 但「零误报」**不成立**：
     「从未被驱动」≠「应该被驱动」（端口可能由**内部逻辑**驱动，或 DUT **根本不用**
     该端口）⇒ 仍需一层「哪些端口**应该**被驱动」的判定 ⇒ **零误报**的前提
     未被证明 ⇒ spike MUST **实测**该前提，而不是把它当结论写。
- ⚠️ **决策门**：若结论是「无法在可接受误报率内实现」⇒ **记录并关闭**，
  把该义务**留在 `AGENTS.md §ANTI-PATTERNS`**（人工核对 + 代码评审）
  ⇒ **不得**硬造一个误报率高的护栏。
