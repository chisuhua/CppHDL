## B1｜builder 链的**上游回接**（`stream-builder-chain-silent-word-loss-2026-11.md`）

### 问题
`stream_fifo` **不驱动**入参 `ready`（写使能只用 `input_stream.valid`，内部
`sync_fifo` 自保护）⇒ ⇒ ⇒ **builder 链里没人驱动 `source.ready`**
⇒ ⇒ 实测 `source.ready` **恒 0** ⇒ ⇒ ⇒ **上游遵守 ready 协议 ⇒ ⇒ 永远推不动
= 死路**。

⚠️ **台账原标题的「静默丢字」已被实测推翻**（A3）：正确接线下 10 个 word
**全部无损通过** ⇒ ⇒ 「丢字」是**观测解读错误**造成的假症状
⇒ ⇒ ⇒ **真缺陷 = 上游反压从未建立**。

### 裁决点
ADR-054 §3.2 第 1 条规定 fifo 类的读使能 = **消费端的 ready**（可覆盖）
⇒ ⇒ ⇒ **修法 A 会让「中间级」的读使能 = 下一级的 `push_stream.ready`**
⇒ ⇒ ⇒ ⇒ **⇒ 「中间级」是否属于 ADR-054 所说的「fifo 类」？**

- **若属于** ⇒ ⇒ 修法 A 与 ADR-054 **冲突** ⇒ ⇒ ⇒ 需 **MODIFIED** 条款
  （明确「中间级」的读使能 = 下一级的容量信号）
- **若不属于**（视为「链内实现细节」）⇒ ⇒ ⇒ 修法 A **可直接落地**

### 已被实测确认的部分（裁决时不必再验）
| 事实 | 结论 |
|---|---|
| 修法 A 的**技术可行性** | ✅ 手写 2 级 + `f1.pop_stream.ready <<= f2.push_stream.ready` ⇒ **零丢字** + 守卫**不误炸** |
| **多驱动守卫**在串联场景 | ✅ 对**下游**调 `connect_ready` ⇒ **不抛**；已覆盖的中间级再调 ⇒ **抛**（= 正确检测）⇒ ⇒ ⇒ 已有行为用例（`[stream][ready][series]`）+ 静态判据 **R9** + 投毒 |
| 修法 B（改 `chlib/fifo.h` 公开 API） | ❌ **不需要** —— `stream_fifo` 的 result **已有** `push_stream.ready`（`stream.h:469`） |
| 契约侧 | 可能 MODIFIED `chlib-stream-ready-ownership`（若纳入「中间级」） |

### 建议
**裁决「中间级 = 链内实现细节」** ⇒ ⇒ ⇒ 修法 A 落地 ⇒ ⇒ ⇒
builder 需**保存链上各 FIFO 的结果对象**（加私有成员）+ 在 `build()` 里做
延迟连接（纯实现细节，非架构取舍）⇒ ⇒ ⇒ **公开 API 零变更**。

## B2｜`stream_demux` 的 ready **方向**（P1-b）

### 事实（实测）
`stream_demux` 现状：`result.output_streams[i].ready = is_selected & input_stream.ready;`
⇒ ⇒ **消费端的 ready 没有反馈给上游**（方向颠倒）⇒ ⇒ ⇒
「选中输出的消费端不就绪 ⇒ ⇒ 上游 stall」**不可演示**。

### 选项
| # | 选项 | 代价 |
|---|---|---|
| 1 | **改成消费端 ⇒ 上游**（标准 AXI/stream 语义） | **行为变更** ⇒ 需 ADR；既有消费者需盘点 |
| 2 | 保持现状 + **契约化**为「demux 不支持背压」 | 契约面变小 ⇒ ⇒ 与 capability R1「组合子 MUST NOT 无条件忽略消费端 ready」**冲突** ⇒ ⇒ 需 **MODIFIED** |

⚠️ **建议**：选项 1（与 mux 对称）⇒ ⇒ ⇒ 但**必须**独立 ADR
（⇒ ⇒ 这是**行为变更**，不是实现缺陷修复）。

## B3｜`stream_fork` 的**同步语义**（P1-c）

### 事实（实测）
`stream_fork` 的同步语义（`input ready` = AND(各 output ready)）**从未工作过**
⇒ ⇒ 现状是「ready 链取自 `input_stream.ready`」（即**上游的** ready）
⇒ ⇒ ⇒ 语义**不是**「等待所有输出就绪」⇒ ⇒ ⇒
**等于新功能** ⇒ ⇒ 判据**从零建**。

### 选项
| # | 选项 | 代价 |
|---|---|---|
| 1 | 实现真同步语义（AND 各 output ready） | **新功能** ⇒ 需 ADR + 契约 + 判据从零 |
| 2 | 契约化现状为「fork 是**广播**，不提供背压」 | 契约面变小 ⇒ ⇒ 需 MODIFIED + **须明确**「调用方如何得知下游就绪」 |

⚠️ **建议**：选项 1（**同步 fork 是 SpinalHDL 的标准语义**）⇒ ⇒ ⇒
但须**独立立项**（判据从零 ⇒ ⇒ 工作量不小于一个完整 change）。

## B4｜`chlib::fwft_fifo` 的**组件去留**（ADR-045 §2.4 推迟至今）

### 事实（实测，A1）
- **不是 FWFT**：实测写入 `0xA1`/`0xB2` 后 `q` 恒为 `0x0`，直到发起读才出现
  `0xA1` ⇒ ⇒ 「读触发输出」，非 show-ahead；
- **真 FWFT 已在** `sync_fifo` 的 `q_async`（0-cycle `aread`）+
  `stream_fifo::pop_stream.payload`；
- **零消费者**：唯一消费者是 `tests/chlib/test_fifo.cpp:407` 的用例
  （**只打印** + 2 个断言）⇒ ⇒ ⇒ **死代码**（ZERO-DEBT 政策）；
- capability `chlib-stream-semantics` **已有**「`fwft_fifo` MUST NOT 被当作
  FWFT 参照」⇒ ⇒ ⇒ **契约已封禁**；
- ⚠️ **公开 API**：`chlib.h` 聚合导出 ⇒ ⇒ ⇒ **删除是 API 变更**。

### 选项
| # | 选项 | 代价 |
|---|---|---|
| 1 | **物理删除**（`fwft_fifo` + `FwftFifoResult` + 测试用例） | API 变更 ⇒ 需 ADR；最合 ZERO-DEBT；**零消费者** ⇒ 零实际影响 |
| 2 | **改名**（如 `fifo_read_triggered`） | API 变更；保留一个**非 FWFT** 的组件 ⇒ ⇒ 「为什么保留它？」需理由 |
| 3 | **重写**成真 FWFT | ⇒ ⇒ **与 `sync_fifo.q_async` 重复** ⇒ ⇒ 制造重复组件 |

⚠️ **建议**：选项 1（**物理删除**）⇒ ⇒ ⇒ 理由：零消费者 + 真 FWFT 已有 +
ZERO-DEBT「No dead code」⇒ ⇒ ⇒ **且它是 capability 已封禁的组件**。

## B5｜`stream_arbiter_sequence` 与 `stream_arbiter_priority` 的**组件重复**

### 事实（实测，P2）

| 1 | **删 `sequence`**，保留 `priority`（+ `round_robin` + `lock`） | API 变更 ⇒ 需盘点消费者（`examples/` / `samples/` 有） |
| 2 | **让 `sequence` 真按顺序轮转** | ⇒ ⇒ **制造第二个轮转组件**（与 `round_robin` 重复）⇒ ⇒ **用户 2026-11-01 已否决** |
| 3 | 保留两者 + 契约明确「两者当前等价」 | ⚠️ 等价但名字不同 ⇒ ⇒ **长期会被误用** |

⚠️ **建议**：选项 1 ⇒ ⇒ ⇒ 理由：**语义重复** ⇒ ⇒ 且 `sequence` 的名字
**没有承诺它**（用户裁决：只订正注释，不改行为）⇒ ⇒ ⇒ 删除是「收敛」。

## B6｜`stream_pipeline.h` 的 **3 个 pipe**（A4 实测挖出）

### 事实（实测，判决性对比）
```
变体 A（既有测试口径：`ready = true` 重绑定到 literal）⇒ ⇒ 能通过 ✔
变体 B（正确接线：`as_master()` + `<<=`，ready 无驱动）  ⇒ ⇒ 零通过 ✘
```
⇒ ⇒ ⇒ `stream_m2s_pipe` / `stream_half_pipe` **只在「调用方把 ready 重绑定成
常量」时活着** ⇒ ⇒ **真实用法下零通过** ⇒ ⇒ 根因 = **pipe 的 ready 链未收口**
⇒ ⇒ ⇒ ① 3 个 pipe **不驱动**上游 ready（`in.ready` 的 `num_srcs() == 0`）
⇒ ⇒ ⇒ ② ⚠️ **`stream_pipeline.h` / `stream_width_adapter.h` 不在 R8 的扫描
范围** ⇒ ⇒ ⇒ ⇒ **⇒ 也不在任何 ready 契约的覆盖范围内** ⇒ ⇒ ⇒ **契约缺口**

⚠️ **既有测试是「假绿」的新形态**：用 `operator=` 喂常量 ready ⇒ ⇒
**恰好绕过**了真实依赖 ⇒ ⇒ ⇒ 断言全绿但**绿灯来自真实用法里不成立的假设**。

### 裁决点
1. pipe 族是否**纳入** `chlib-stream-ready-ownership` 的覆盖范围？
   （⇒ ⇒ 若纳入 ⇒ ⇒ 需 MODIFIED + 把 `stream_pipeline.h` 加入 R8 扫描面）
2. 修法：按 P1-a 的**形态 E**（默认值 + 可覆盖）修，还是**契约化**为
   「pipe 不提供背压」？

### 建议
**纳入契约 + 按形态 E 修** ⇒ ⇒ ⇒ 理由：pipe 是「转发类」⇒ ⇒
capability R1「组合子 MUST NOT 无条件忽略消费端的 ready」**本应覆盖它**
⇒ ⇒ ⇒ 当前是**覆盖缺口**（⇒ ⇒ 与「显式豁免」不同 ⇒ ⇒ 豁免需 `::notice` 点名）。

## B7｜**未驱动字段诊断**（框架层通用能力 · P5）

### 事实
- 读**未驱动**的 `ch_bool` 代理节点 ⇒ ⇒ **无法驱动任何输出**
  （`ch_out::operator<<=` 要求 driver 非 null）⇒ ⇒ **两条路都不通**；
- 读**空**节点（`ch_stream` 默认构造的字段）⇒ ⇒ 💥 **ABORT**
  （`ch_bool implementation is null`）；
- ⇒ ⇒ ⇒ 「**未连接 ⇒ 响亮失败**」在当前框架能力下**不可实现**
  （ADR-054 §3.1 形态 B 被证伪的原因之一）。

### 裁决点
「诊断」的**形态**：
| # | 选项 | 代价 |
|---|---|---|
| 1 | 读空节点 ⇒ ⇒ **抛异常**（而非 ABORT） | 行为变更 ⇒ ⇒ 现有依赖 ABORT 的代码会变 |
| 2 | 读未驱动节点 ⇒ ⇒ **返回可区分的「未驱动」态** | 需改 `sdata_type` 契约 ⇒ ⇒ 影响面大 |
| 3 | 提供**显式诊断 API**（如 `node_is_driven(ptr)`）⇒ ⇒ 护栏用它 | 增量 ⇒ ⇒ 不改既有语义 |

⚠️ **建议**：选项 3（**增量、不改既有语义**）⇒ ⇒ ⇒ 理由：本仓多数「静默失效」
的根因都是「**没人能问「这个节点有没有驱动」**」⇒ ⇒ ⇒ 一个只读的诊断 API
能让**所有**护栏受益 ⇒ ⇒ ⇒ 而选项 1/2 都是**全局行为变更**（⇒ ⇒ 爆炸半径大）。

## B8｜命名诚实性是否需要**「审计制」条款**

### 事实
P2 修了 `stream_arbiter_sequence` 一个 ⇒ ⇒ A4 普查又发现 `fwft_fifo`（已修）
+ **pipe 族的「注释声称 vs 实际」不一致** ⇒ ⇒ ⇒ **「只修已知那个」会复发**。

### 选项
| # | 选项 | 代价 |
|---|---|---|
| 1 | 在 `chlib-stream-arbitration` R2 加「**同类 MUST 有普查机制**」 | 契约增量；⚠️ 「普查」的**可执行形式**难定义（⇒ ⇒ 可能变成不可验证的 MUST ⇒ ⇒ **慎**） |
| 2 | 不加契约，改为**收口清单 + 审计台账**（本轮已做） | 无契约 ⇒ ⇒ 靠台账 ⇒ ⇒ **会漂移** |
| 3 | 加「**每个组件 MUST 有一条行为用例锁定其声称语义**」 | ⚠️ 覆盖面要求 ⇒ ⇒ 工作量大（⇒ ⇒ 但**可执行** ⇒ ⇒ 不违反本仓「契约 MUST 有可执行判据」的纪律） |

⚠️ **建议**：选项 3 的**弱化版**（「新增/修改组件时 MUST 有一条行为用例锁定
其**名字/注释里声称的**语义」）⇒ ⇒ ⇒ 理由：它**可执行**（⇒ ⇒ 能被护栏检查
「新组件有无行为用例」）⇒ ⇒ ⇒ 且不要求「全仓普查」这种不可验证的义务。
