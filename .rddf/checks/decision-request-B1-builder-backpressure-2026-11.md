## 1. 裁决问题（**精确表述**）

> **`StreamBuilder` 链内的「中间级」FIFO（= 非链首、非链尾）**
> ① 它的**读使能**（`pop_stream.ready` 的驱动源）**应当是什么**？
> ② 它**是否属于** ADR-054 §3.2 第 1 条所说的「**fifo 类**」？
> ③ 若不属于 ⇒ ⇒ 该条款**如何**表述才不留下「例外先例」？

⚠️ **为什么必须裁决**：§3.2 第 1 条规定「fifo 类组合子 … 读使能 MUST 接一个
**带默认驱动**的字段 ⇒ ⇒ `<组合子>_connect_ready` 把**消费端 ready** 覆盖到
该字段」⇒ ⇒ 若「中间级」属该类 ⇒ ⇒ 则「中间级读使能 = **下一级**的容量
信号」与该条款**冲突** ⇒ ⇒ ⇒ **⇒ 若不属于 ⇒ ⇒ 该条款**原文保持**且不需例外**。

## 2. 事实（**全部实测**，2026-11-01）

### 2.1 缺陷本体

```
E10 builder 链（**正确接线**：`as_master()` + `<<=`）：
  t   source.ready   out.valid   out.payload
  0   0              1          10
  ...
  9   0              1          19      ← 10 个 word 全部无损通过
 10   0              0          16      ← 弹光后的残留
⇒ ⇒ `source.ready` **恒 0** ⇒ ⇒ **上游遵守 ready 协议 ⇒ ⇒ 永远推不动 = 死路**
```

⇒ ⇒ **根因**：`stream_fifo` **不驱动**入参 `ready`（写使能只用
`input_stream.valid`，内部 `sync_fifo` 自保护）⇒ ⇒ builder 链里**没人驱动**
`source.ready` ⇒ ⇒ ⇒ 「FIFO 满 ⇒ 上游暂停」在 builder 链里**不可演示**。

⚠️ **「静默丢字」已被推翻**（原台账标题的错误根因）⇒ ⇒ 真缺陷**只有**这一条。

### 2.2 修法 A 的**技术可行性**（实测）

| 事实 | 结论 |
|---|---|
| 手写 2 级 + 显式回接（`f1.pop_stream.ready <<= f2.push_stream.ready`） | ✅ **零丢字**（观测 `0x10..0x13` 各恰一次） |
| 多驱动守卫在**串联**场景 | ✅ 对**下游** `connect_ready` **不抛**；已覆盖的中间级再调 **抛**（= 正确检测） |
| ⇒ ⇒ **⇒ 回接与守卫不冲突** | ⇒ ⇒ 修法 A 的**唯一**障碍是**语义归属**，不是机制 |
| 修法 B（改 `chlib/fifo.h` 加写口 ready） | ❌ **不需要** —— `stream_fifo` 的 result **已有** `push_stream.ready`（`stream.h:469`） |

⇒ ⇒ **公开 API 零变更**（`StreamBuilder` 的公开接口不动；只需**加私有成员** +
在 `build()` 里做延迟连接）⇒ ⇒ ⇒ **⇒ 不需要「签名变更」类 ADR 的重流程**。

### 2.3 ⚠️ 台账与既有测试的**接线缺陷**（**影响修法 A 的实施面**）

- `tests/test_stream_builder.cpp:116-117` 用 `operator=` 接线且**无** `as_master()`
  ⇒ ⇒ ⇒ 它**结构上无法**观测上游反压（⇒ ⇒ **覆盖面缺口**）；
- ⇒ ⇒ ⚠️ 修法 A 落地时**顺带**修掉这处接线（否则新判据无法写）。

## 3. ⭐ 关键洞察：**中间级是 ADR-054 §2 表里的【第三类】**

ADR-054 §2 的**承重区分表**按「**ready 的方向**」分了两类：

| 类别 | ready 的方向 | 需要对 ready 做什么 |
|---|---|---|
| mux / demux / arbiter 类 | **消费端 ready** → 各输入 ready | 驱动结果字段的 ready |
| fifo 类（`stream_fifo`） | **消费端 ready** → **内部读使能** | 读取消费端 ready 作内部逻辑的输入 |

⇒ ⇒ **「链内中间级」的 ready 方向 = 「下游的容量信号（`push_stream.ready`
= `!full`）」→ 本级读使能** ⇒ ⇒ ⇒ **⇒ 它既不是第一类（方向相反：不是
「消费端 ⇒ 输入」，而是「下游容量 ⇒ 本级」）⇒ ⇒ ⇒ 也不是第二类（不是
「消费端 ⇒ 内部读使能」）⇒ ⇒ ⇒ ⇒ ⇒ **⇒ 它是【第三类】**
⇒ ⇒ ⇒ ⇒ ⇒ ⇒ **⇒ ⇒ 最诚实的裁决 = 把第三类【显式立为一类】**
⇒ ⇒ ⇒ ⇒ ⇒ ⇒ **⇒ 而不是「在 fifo 类里开例外」**
⇒ ⇒ ⇒ ⇒ ⇒ ⇒ ⇒ ⚠️ **「例外」会成为先例** ⇒ ⇒ ⇒ 「fifo 类的读使能可以
不是消费端的 ready」⇒ ⇒ ⇒ ⇒ ⇒ ⇒ ⇒ ⇒ **⇒ 下一个人会据此扩大豁免**。

## 6. 后果 / 代价（**裁决前的中立评估**）

### 正面
- builder 链从**死路**（上游永远推不动）变为**可反压** ⇒ ⇒ ⇒「FIFO 满 ⇒ 上游
  暂停」**可演示** ⇒ ⇒ ⇒ 2 个 disabled sample 之外**又解锁一条活文档路径**；
- **公开 API 零变更** ⇒ ⇒ 存量调用点**不需迁移**；
- 顺带补上 **R8 扫描面**的缺口（`stream_builder.h`）⇒ ⇒ ⇒ 护栏覆盖面扩大。

### 负面
- builder 链的**行为**从「无条件弹」变为「按下游容量弹」⇒ ⇒ **行为变更**
  ⇒ ⇒ ⇒ 既有断言若依赖旧行为 ⇒ ⇒ MUST 逐项复核（**实测**：`tests/test_stream_builder.cpp`
  的既有用例**只做结构断言** ⇒ ⇒ 零破坏风险 ✔）；
- builder **必须保存链上各 FIFO 的结果对象**（私有成员）⇒ ⇒ ⇒ **链很长时
  内存占用线性增长**（每级一个 result 对象 ⇒ ⇒ 结果对象很小 ⇒ ⇒ 可接受）。

### 风险
| # | 风险 | 对策 |
|---|---|---|
| 1 | 「第三类」的表述**将来被误用**成「fifo 类的读使能可以不是消费端的 ready」 | ⇒ ⇒ ADR-055 MUST **明确**它**只**适用于**链内中间级**（不对外暴露的组合子）⇒ ⇒ 且 MUST 写明「**不是**对 §3.2 第 1 条的例外」 |
| 2 | 回接引入**组合环** | ⇒ ⇒ 实测已确认**不成环**（回接的源是**下一级的 `push_stream.ready`** = 寄存器 `full` 的组合输出 ⇒ ⇒ 本级的读使能是**寄存器输入**）⇒ ⇒ ⇒ **但 MUST 在实现时复核** |
| 3 | 中间级的 `pop_stream.ready` 被覆盖 ⇒ ⇒ **调用方无法再对中间级调 `connect_ready`**（守卫会抛） | ⇒ ⇒ 这是**正确**的多驱动检测 ⇒ ⇒ 但 MUST **写进契约**（否则调用方会撞上「响亮异常」而不知为何） |
