## 1. N4：`multi_if` 的宽度面 —— 真实形态是「**静默丢位**」，不是「编译不过」

### 1.1 探针源码（`/tmp/opencode/n4r/v.cpp`，最小复现）

```cpp
class Dut : public ch::Component {
public:
    __io(ch_out<ch_uint<8>> o_trunc;)
    void describe() override {
        ch_uint<8> a(0xA5_h), b(0x5A_h);          // a-b = 0x4B (8b) · a+b = 0x0FF (9b)
        ch_bool f(false), t(true);
        ch_uint<8> v = if_then(f, a - b).elif(t, a + b);   // 首分支 8 位 ⇒ T = ch_uint<8>
        io().o_trunc <<= v;
    }
};
```

### 1.2 节点创建日志（`[INFO] Created node ID …`，实测）

```
node  8:  top.add_add     (op,  9 bits)    ← a+b 真的是 9 位
node 10:  top.bits_range  (lit, 64 bits)   ← 值为 64'h700000000 = bits<7,0> 的范围常量
node 11:  top.bits        (op,  8 bits)    ← ⚠️ 框架自动插入的截断节点
node 12:  top.mux_select  (mux, 8 bits)    ← 只有截断后的 8 位进 mux
```

### 1.3 生成 Verilog（决定性硬证据）

```verilog
/* verilator lint_off WIDTHEXPAND */
/* verilator lint_off WIDTHTRUNC */
module top (
    input default_clock,
    input default_reset
);
    logic [8:0] top_add_add;
    logic [8:0] top__add_add;
    logic [63:0] top_bits_range;
    logic [7:0] top_bits;
    logic [7:0] top_mux_select;

    assign top_uint_lit    = 8'ha5;
    assign top_uint_lit_1  = 8'h5a;
    assign top_add_add     = top_uint_lit + 8'h5a;
    assign top__add_add    = top_add_add;
    assign top_bits_range  = 64'h700000000;
    assign top_bits        = top__add_add[7:0];        // ⚠️ bit[8] 被静默丢弃
    assign top_mux_select  = top_bool_lit ? top__sub_sub : top_bits;
endmodule
```

### 1.4 两层护栏同时失效

| 层 | 状态 | 位置 |
|---|---|---|
| C++ 前端 | **静默窄化**（`ch_uint<8>` 的转换构造接受 9 位 ⇒ 插 `bits<7:0>`） | `include/chlib/if.h` 的 `branch_info{T value}` + `operator T()` |
| Verilog 后端 | **`WIDTHTRUNC` 被全局关闭** | `src/codegen_verilog.cpp:299-300` |

⚠️ 后者的关闭理由是**正当**的（CH_MEM select-tree 的已知宽度差，见该处注释）
⇒ ⇒ 所以**不能**靠「打开 WIDTHTRUNC」来修 —— 那会让既有设计全部报错。
**修法必须在 C++ 前端**：后端**无法区分**「框架已知的良性加宽」与「用户笔误的丢位」。

### 1.5 与既有纪录的偏差（必须订正）

| 来源 | 原表述 | 实测 |
|---|---|---|
| 刚归档的 capability `chlib-conditional-semantics`（E2 的 NOTE） | 「`multi_if<T>` 要求所有分支值同类型 `T`（⇒ `a+b` 是 9 位、`a-b` 是 8 位 ⇒ **模板推导冲突**）」 | ❌ **不准确** —— 只有 **ctor** 从首分支推导 `T`；`elif`/`else_` 的参数是 `const T&` ⇒ 后续分支走**隐式转换**（含窄化）⇒ **不报错** |
| `samples/if_demo.cpp` 的禁用理由 | 「`:39 字面量宽度不匹配`」 | 实测真实错误是 **5 类**（`priority_if_then` 不存在 / `else_(lambda)` / `ch_in<ch_bool>::posedge` / `next.value` / `get_lnode(multi_if)`）⇒ 该条**已过时** |

### 1.6 R1：`ch_width_v` 对纯 C++ 算术类型

| 类型 | `ch_width_v` | 来源 |
|---|---|---|
| 任意 integral（`int` / `unsigned` / `long long` …） | **32**（`int` 另有 `sizeof(int)*8` 特化 = 32） | `include/core/traits.h:28-38` |
| `float` / `double` | **编译期硬错误**（主模板 `debug_hook()` 实例化未定义的 `_print_type<T>`） | `include/core/traits.h:12-24` |

⇒ ⇒ **对 N4 的直接含义**：若 `static_assert(ch_width_v<U> <= ch_width_v<T>)` 无条件生效，
则 `if_then(c, ch_uint<8>(x)).elif(c, 1)`（分支是 `int` 字面量，`ch_width_v<int>` = 32）
会被**误拒**。

⚠️ **但实测该写法今天可编译**（`ch_uint<8>` 接受 `int` 隐式构造）。
⇒ ⇒ 故 N4 的判据 **MUST NOT** 用裸 `ch_width_v<U> <= ch_width_v<T>`，
MUST **对算术字面量分支豁免**（按「值是否可容纳」判，或直接放行算术字面量）。

### 1.7 R2：显式宽度逃生口实测可用

```cpp
ch_uint<9> w = if_then<ch_uint<9>>(f, a - b).elif(t, a + b);   // ✅ 编译通过
```
⇒ ⇒ `if_then<ch_uint<W>>(...)` 显式模板实参确实存在且可用 ⇒ 可作契约的逃生口。

## 2. N6：`get_lnode` 的无约束重载

### 2.1 两个签名完全相同的候选

| # | 位置 | 约束 | 函数体 |
|---|---|---|---|
| ① | `include/core/lnode.h:24-28` | `requires { t.impl(); }` | `return lnode<T>(t.impl());` |
| ② | `include/core/bundle/bundle_base.h:551-553` | **无** | `return lnode<Derived>(b.impl());` |

`bundle_base` **继承**了 `logic_buffer::impl()`（`bundle_base.h:67`）
⇒ ⇒ `HardwareType<Bundle>` = **true** ⇒ ①与②**同时可行**。

### 2.2 C++20「约束更严者胜」实测（探针复刻两版签名形状）

```
HasImpl (有 impl()，如 bundle / ch_uint / port)  ⇒ 选中 ① lnode.h（受约束）
NoImpl  (无 impl()，如 multi_if)                 ⇒ 选中 ② bundle_base.h（无约束）
                                                     ⇒ 其函数体 b.impl() **必然编不过**
```

⇒ ⇒ 结论：**② 对有 `impl()` 者「死」、对无 `impl()` 者「有害」** ⇒ 无第三种可能。

### 2.3 「有害」路径的真实触发（不是理论）

`samples/if_demo.cpp:38` 编译实测错误：

```
include/core/bundle/bundle_base.h:552:29: error:
  ‘const class chlib::multi_if<ch::core::ch_uint<9> >’ has no member named ‘impl’
```

⇒ ⇒ **错误指向框架内部文件**（`bundle_base.h:552`），**不是**用户的调用点
⇒ ⇒ 用户会误判为框架 bug。

删除②后预期消息：
```
error: no matching function for call to 'get_lnode(const chlib::multi_if<...>&)'
note: candidate: 'get_lnode(const T&) requires requires { t.impl(); }'
```
⇒ ⇒ **指向调用点 + 给出约束不满足的原因**。

### 2.4 仓内无合法消费者的证据

| 检查 | 结果 |
|---|---|
| `lnode<Bundle>` 使用 | **0** |
| `ch_width_v<Bundle>` 使用 | **0**（`ch_width_v<std::decay_t<T>>` 的 6 处活跃使用均在 `chlib/switch.h` 的模板上下文，与 bundle 无关） |
| `get_lnode` 实参形态普查 | 全部是**标量 / 端口 / lnode**（`lhs` 31 · `rhs` 29 · `operand` 7 · `value` 4 · … ） |

### 2.5 ⚠️ 附近但**不同类**的设施（不并入 N6）

`include/core/bundle/bundle_base.h:546-549`：
```cpp
template <typename Derived>
struct ch_width_impl<Derived, std::enable_if_t<is_bundle_type<Derived>>> {
    static constexpr unsigned value = get_bundle_width<Derived>();
};
```
⇒ 它是**类模板特化**（可被任意用户 TU 实例化），不是「具体重载」⇒ ⇒
删除判据**不同**（「今天没有消费者」≠「可证永远不可能有合法实例化」）
⇒ ⇒ **只登记，不在 N6 裁决范围**。

## 3. 补测：`multi_if` 的**五种**缺陷形态（全部实测，2026-10-30）

> ⚠️ 比原定范围（「宽度」）更宽 —— 三处是同一次探针连带挖出的。
> 用户裁定 N4 范围 = 「只修 `multi_if` 内部」⇒ ⇒ **以下五种全在范围内**。

| # | 形态 | 实测结果 | 严重度 |
|---|---|---|---|
| **A** | 首分支窄、后续宽（`if_then(f, a-b).elif(t, a+b)`） | ✅ 编译、**静默丢 bit8** | 高（数值错） |
| **B** | **单分支**（`if_then(c, x)`，无 `elif` / `else_`） | ✅ 编译、**条件被完全忽略**，结果恒 `= x` | **最高（控制流不生效）** |
| **C** | `T` 推导成 **port 类型**（`if_then(c, io().a)`） | ❌ 编译失败（`multi_if<port<…>>` 不能转 `ch_uint`） | 中（可用性） |
| **D** | `T` = **纯 C++ 算术**（`if_then(c, 1).elif(c, 2)`） | ❌ 编译失败（`multi_if<int>` 不能转 `ch_uint`）⇒ ⇒ ctor 的 `static_assert` **放行**了它，但结果**不可用** | 中（「接受但不可用」死路） |
| **E** | 显式 `T` **过窄**且分支更宽（`if_then<ch_uint<1>>(c, a)`，a 8 位） | ✅ 编译、**静默截断到 1 位**（丢 7 位） | 高 |

### 3.1 形态 B 的硬证据（生成 Verilog）

```verilog
assign top_cond_marker = 1'b1;                         // cond 节点存在
assign top_uint_lit    = 8'ha5;                        // 单分支的值
// ⚠️ 单分支结果直接 = top_uint_lit ⇒ **无 mux、cond 从未参与合成**
assign top_mux_select  = top_cond_marker ? top_uint_lit_1 : top_uint_lit_2;  // 双分支有 mux ✔
```

**根因**（`include/chlib/if.h` 的 `operator T()`）：
```cpp
T current_value = branches_.back().value;
for (auto it = branches_.rbegin() + 1; it != branches_.rend(); ++it) { ... }
// 单分支 ⇒ branches_.size()==1 ⇒ rbegin()+1 == rend() ⇒ **循环体一次都不执行**
return current_value;   // 恒等于 branches_.back().value
```
⇒ ⇒ 条件**在结构上就不可能**被用到。

⚠️ 与 ADR-051 记录的 `_if` 双重失效（「条件被彻底忽略」）**完全同型** ⇒ ⇒
这是**同一类病的第三个实例**（第二个是 `uart_tx` 的 FSM，第三个是本处）。

### 3.2 边界形态（全部编译通过的「合法」用法）

| # | 形态 | 结果 |
|---|---|---|
| E-1 | 显式 `T=16`，分支全 8 位 | ✅ 零扩展，width=16 ✔ 正确 |
| E-2 | 仅 `else_`（`if_then(c,a).else_(b)`） | ✅ width=8 ✔ |
| E-3 | 单分支（无 else_） | ⚠️ **见形态 B —— 条件被忽略** |
| E-4 | `T = ch_bool` | ✅ 编译 |
| E-7 | 显式 `T=9`，分支 8 位 | ✅ 零扩展，width=9 ✔ |

### 3.3 附带发现（独立现象，需另行登记）

1. `ch_uint` 之间的 `a > b` ⇒ 报 `[ERROR] [node_builder] Invalid operands for binary operation`
   （`lnode/node_builder.tpp:32`）⇒ ⇒ **关系运算符 `>` 在 `ch_uint` 上不可用**（对比 `==` 可用）。
   影响：`if_then(a > b, x)` 这一**最自然**的写法直接失败。
2. `ch_uint<8> a = io().a;`（顶层 `ch_in`）⇒ 该 port 未驱动时节点为 **null** ⇒
   后续 `io().o <<= v` 报 `Invalid port connection: receiver node is null`（`io.h:451`）。
   ⇒ ⇒ 顶层输入端口**不能**在 `describe()` 内直接用作值源（须经 testbench 驱动或寄存器中转）。

## 4. N6：**SFINAE 毒化**（比「错误消息」更硬的删除理由）

### 4.1 实测（`/tmp/opencode/n6/poison.cpp`，复刻两版签名形状）

```
requires { get_lnode(NoImpl{}) } = TRUE
⇒ ⚠️ 毒化确认：探测为 true，但真调用时函数体 b.impl() 编不过 ⇒ 假阳性
```

**机制**：无约束版的返回类型是**显式的** `lnode<Derived>` ⇒
`requires { get_lnode(x); }` 只检查**重载决议 + 返回类型合法性**，**不实例化函数体**
⇒ ⇒ 对无 `impl()` 的类型探测**通过**（假阳性）⇒ ⇒ 任何基于 `requires` 的
类型分派/能力探测都会**误判该类型「支持 get_lnode」**。

⇒ ⇒ 这使无约束版从「死代码」升级为「**主动毒化能力探测**」
⇒ ⇒ 删除理由**不依赖**「错误消息是否更好」这个主观判断。

### 4.2 可写成机器护栏（天然带变异判别力）

```cpp
struct NoImplTag { };                      // 无 impl()
static_assert(!requires(NoImplTag x) { get_lnode(x); },
              "无约束的 get_lnode 入口 MUST NOT 存在（它对无 impl() 的类型产生假阳性探测）");
```
⇒ ⇒ **今天该断言为假 ⇒ 加进去即转红** ⇒ 删除 `bundle_base.h:551-553` 后转绿
⇒ ⇒ 护栏与修复**同批**落地 ⇒ 将来再加无约束入口会**立即**被抓。

### 4.3 删除后的消息形态（oracle 评估 + 需在实施时实测确认）

| 编译器 | 预期 |
|---|---|
| GCC | `error: no matching function for call to 'get_lnode(const multi_if<ch_uint<9>>&)'` + 候选注释（`lnode.h:24` 候选带 `constraints not satisfied … no member named 'impl'`） |
| Clang | `candidate template ignored: constraints not satisfied … because 't.impl()' would be invalid: no member named 'impl'` |

⇒ 「缺 `impl`」的信息**被保留**，但挂在**正确的候选**上，
且**不再把错误帧指进 `bundle_base.h:552`**（这正是 `if_demo` 实测到的误导形态）。

⚠️ **MUST NOT** 用替代方案「补一个 `= delete` 兜底重载」或「函数体 `static_assert` 陷阱」
⇒ 两者都**重新毒化** `requires` 探测（前者 C++26 前无法带消息；后者体不实例化 ⇒ 探测仍 true）。

### 4.4 次序：N6 **先于** E1（N3）

中间态**完全可接受**：`multi_if` 赋给 `ch_out` 在删除前后**都**是编译期硬错误，
零「编译中」代码受影响。

⚠️ 但有一条**已失效的理由**需记账：oracle 初判「删除会改变全仓重载决议面」
⇒ ⇒ 已被本文件 §2.2 实测推翻（受约束版在**约束偏序**下对一切合法类型**恒胜**，
与 include 顺序无关）⇒ ⇒ 决议面**不变** ⇒ 爆炸半径 **0**。

## 5. 形态 D（`T` = 算术字面量）的**真实失败机制**（订正 oracle 的推断）

oracle 推断：「`operator T()` 里 `ch_uint → int` 需要隐式转换，而 `uint.h:122` 是 explicit ⇒ 一用即硬错误」。

⚠️ **实测更精确的原因不同**：
- `include/core/uint.h:57` 确实有 `ch_uint(IntT v, ...)`（**非 explicit**，接受整数）；
- `include/core/uint.h:122` 的 `explicit operator uint64_t()` 与本路径**无关**；
- 真正的障碍是 **C++ 隐式转换序列「最多一次用户定义转换」**：
  `multi_if<int> → int`（`operator T()` 已是一次）**再** `int → ch_uint<8>`（ctor 是第二次）
  ⇒ ⇒ **两次用户定义转换 ⇒ 不允许** ⇒ 编译错误：
  `conversion from 'chlib::multi_if<int>' to non-scalar type 'ch::core::ch_uint<8>' requested`
  ⇒ 错误信息**指向赋值点**，**不**解释原因。

⇒ ⇒ 因此形态 D 的修法**不是**改 explicit 性（那会破坏大量既有代码），
而是 **ctor 拒绝 `T` 为算术类型**（`static_assert(HardwareType<T>)`）
⇒ ⇒ 实测逃生口可用：`if_then<ch_uint<8>>(c, 1).else_(2)` **编译通过**（width=8）✔

## 6. ADR-052 第 1 轮评审的 BLOCKER 及其复核实测（2026-10-30）

### 6.1 BLOCKER：`HardwareType<T>` **不能**用来拒绝 port

原 D4 写「ctor `static_assert(HardwareType<T>)` 拒绝 port 与算术」。**该判据对 port 无效**：

```
HardwareType<ch_uint<8>>              = TRUE
HardwareType<port<u8,input_direction>>  = TRUE   ← ⚠️ 形态 C 被放行
HardwareType<port<u8,output_direction>> = TRUE
HardwareType<int>                     = FALSE   ← 算术确实被拒
requires { in.impl() }                = TRUE    ← port 有 impl()（io.h:125/201）
```

**根因**：`HardwareType` 的定义是「有 `impl()` 且非算术」（`operators.h:40-42`）
⇒ port **有** `impl()` ⇒ 它是 `HardwareType`。

⇒ ⇒ **port 判据 MUST 用** `requires { typename T::value_type; typename T::direction; }`
（与 `to_operand` 的既有 port 特判同款，`operators.h:60-64`）。

### 6.2 形态 C 的处置：**归一化**（不是拒绝）—— 已实测可行

理由是**框架一致性**：`select` 对 port **可用**（`to_operand` 特判），
而 `if_then(c, io().a)` 不可用 ⇒ 这是框架内不一致。

**归一化的实测证据**（编译期类型映射，`/tmp/opencode/n4x/norm.cpp`）：

```cpp
// port 检测 + value_type 提取
template <typename U> static auto probe(int) -> std::enable_if_t<
    requires { typename U::value_type; typename U::direction; }, typename U::value_type>;
template <typename U> static U probe(...);

using VT = mif_vt<decltype(io().a)>;
static_assert(std::is_same_v<VT, ch_uint<8>>, "归一化应得 ch_uint<8>");   // ✅ 通过
ch_uint<8> v = multi_if<VT>(cond, VT(io().a)).else_(VT(io().b));         // ✅ 编译 + 建出 mux
```

⇒ ⇒ 归一化是一个**编译期类型映射** ⇒ 其运行期行为由 `multi_if` 对 `ch_uint` 的
既有覆盖承担（`samples/conditional_demo.cpp` 已覆盖）。

⚠️ **运行期验证受阻的已知原因**：顶层 `ch_in` 在 `describe()` 内节点为 **null**
（未驱动的顶层输入）⇒ 不能在 DUT 内直接作值源（见 §3.3 第 2 条，已登记为 Non-Goal）。

### 6.3 `= delete` 兜底重载的真实行为（订正 ADR-053 初稿的表述）

```
有 = delete 兜底时：requires { get_lnode(NoImpl{}) }
⇒ GCC 报 **硬错误**：error: use of deleted function ...
```

⇒ ⇒ `= delete` **不**毒化为 `true`（探测不是静默假阳性），但它把「假阳性」
换成「**探测直接编译不过**」⇒ **更坏**（能力探测应当返回布尔值）。
⇒ ⇒ 它不是「重新毒化」，而是「**让探测不可用**」；真正的重新毒化是
「函数体 `static_assert` 陷阱」（体不实例化 ⇒ 探测仍 `true`）。

### 6.4 `samples/conditional_demo.cpp` 的实际形态（订正 ADR-052 §4）

```cpp
io().result = ch_uint<8>(if_then(io().op == 0_d, ch_uint<8>(io().a + io().b))
                            .elif(io().op == 1_d, ch_uint<8>(io().a - io().b))
                            .elif(io().op == 2_d, ch_uint<8>(io().a & io().b))
                            .else_(ch_uint<8>(io().a | io().b)));
```

⇒ **无**显式模板实参 ⇒ `T` 由首分支推导为 `ch_uint<8>`；每分支显式
`ch_uint<8>(...)` 收敛 ⇒ ⇒ 即 D6 表的「每分支显式收敛」行，**不是**
`if_then<ch_uint<9>>` 形态。

### 6.5 `ch_bool` 端口的归一化兜底（实测，ADR-052 D4 引用）

port 的转换运算符只有两个（`include/core/io.h`）：

| 运算符 | 约束 | 对 `port<ch_bool>` |
|---|---|---|
| `operator ch_uint<W>()`（`:232` / `:277`） | `requires(is_same_v<T, ch_uint<W>>)` | ❌ 不匹配（`T = ch_bool`） |
| `operator lnode<T>()`（`:229` / `:200`） | **无** | ✅ 可用 ⇒ 得 `lnode<ch_bool>` |

⇒ ⇒ `port<ch_bool>` **不能**直接转 `ch_bool`，但**可**经 `lnode<ch_bool>` 取 `impl()`
构造（`ch_bool(lnodeimpl*)` 存在）。

**端到端实测（编译通过）**：

```cpp
template <typename VT, typename T> VT normalize_branch(const T &v) {
    if constexpr (std::is_constructible_v<VT, const T &>) return VT(v);
    else if constexpr (requires { typename T::value_type; })
        return VT(lnode<typename T::value_type>(v).impl());   // ← ch_bool 端口走这条
    else return VT(v);
}
// flag : ch_in<ch_bool>
using VT = mif_vt<decltype(io().flag)>;                 static_assert(is_same_v<VT, ch_bool>);
ch_bool r = multi_if<VT>(c, normalize_branch<VT>(io().flag)).else_(ch_bool(false));   // ✅
```
