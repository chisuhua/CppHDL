## 1. 今天就能用的 7 条纪律（面向「将来不返工」）

⚠️ 这 7 条**不依赖**层次化 API 落地 ⇒ ⇒ ⇒ **今天照做，将来不返工**。

### D1 —— 子模块的接口用 `ch_in` / `ch_out` 表达，不要用 bundle 成员跨层

```cpp
// ✅ 推荐：端口式 —— 子模块的边界是「明确的端口」
class Fifo : public ch::Component {
    __io(ch_in<ch_bool> push; ch_in<ch_uint<8>> data; ch_out<ch_uint<8>> out;)
    ...
};
// 父层：
fifo.io().push <<= io().push;
io().out <<= fifo.io().out;

// ⚠️ 可用但"贵"：bundle 成员跨层 —— 层次化时会产生**隐式端口**
fifo.instance().stream_in <<= producer.instance().stream_out;
```

**为什么**：bundle 成员**不是端口** ⇒ 层次化时跨层边必须**合成隐式端口**（ADR-060 §2.1）
⇒ ⇒ ⇒ 产物里出现 `__if_payload` 这类**框架内部术语**的端口 ⇒ ⇒ ⇒ 外部评审不可读。

### D2 —— 子模块的 `ch_out` 若无人消费，在扁平产物里会**污染顶层端口表**

⚠️ 扁平 codegen **只过滤 input，不过滤 output**（`src/codegen_verilog.cpp:363-370`）
⇒ ⇒ ⇒ **任意层**的 `ch_out` 都成为顶层 `output` 端口 ⇒ ⇒ ⇒ 层次越深，顶层端口越多。

```cpp
// ⚠️ 子模块的这个输出没人用，但它会出现在顶层端口表里
class Sub : public ch::Component {
    __io(ch_in<ch_uint<8>> a; ch_out<ch_uint<8>> debug_probe;)
};
```
⇒ ⇒ **建议**：调试用的 `ch_out` 要么**删掉**，要么**显式接到顶层的某个观测端口**上
⇒ ⇒ ⇒ 层次化后子输出**不会**被抬到顶层（ADR-060 §2.1）⇒ ⇒ ⇒ **接了反而更干净**。

### D3 —— `ch_module` 必须写在 `describe()` 里

```cpp
// ✅
void describe() override {
    ch::ch_module<Sub> sub{"sub"};     // 局部变量
}
// ❌ 成员变量形态：挂祖父 + context 未就绪 ⇒ 子模块直接消失（ADR-059 §1.1 事实②④）
ch::ch_module<Sub> sub{"sub"};         // 成员
```

**为什么**：成员形态下 `ch_module` 的 parent 取 `Component::current()`（还是**父**组件）
⇒ ⇒ 挂错层 ⇒ ⇒ 且该父组件在构造期 `context() == nullptr` ⇒ ⇒ 早退 ⇒ ⇒ 子组件消失。
（这条是 `Rv32iPipeline` 至今**不能**直接 `ch_device` 化的根因。）

### D4 —— 子模块的**每一个**输入都必须被显式驱动

```cpp
// ❌ 悬空：读到的值是「未定义值」（实测：全 1），不是 0
sub.io().en <<= ???;
// ✅
sub.io().en <<= io().en;
```

**为什么**：未驱动 ⇒ 层次化时它会**冒泡**成顶层输入（名字与扁平产物相同，ADR-060 §2.2）
⇒ ⇒ ⇒ 顶层端口表里出现一个**用户没写过**的名字 ⇒ ⇒ ⇒ 外部 TB 会问"这根线是什么"。

### D5 —— 不要在父层直接改子层的 `reg->next`

```cpp
// ⚠️ 可用但"贵"：父层直接写子模块的寄存器
child.instance().acc->next = ch_uint<8>(119_d);
```
**为什么**：这是**跨模块非端口边** ⇒ ⇒ 层次化要合成隐式端口（`__x_<n>`）
⇒ ⇒ ⇒ 且父层写 `next` 与子层自己写 `next` 是**两个写点** ⇒ ⇒ `next` 是 last-wins
⇒ ⇒ ⇒ 父子同时写 = **行为未定义** ⇒ ⇒ ⇒ 建议：改成**子模块自己提供控制端口**。

### D6 —— 实例名要有语义

```cpp
ch::ch_module<Adder> add0{"add0"};        // ✅ 局部名会进实例名
ch::ch_module<Adder> u{"x"};                // ⚠️ 层次化后外部只能看到 "x"
```
**为什么**：层次化的**模块名**来自**你给的字符串**（类级 `CH_HIERARCHY_LAYER("name")`
⇒ 或实例级 `ch_layer<Helper> h{"h","helper_layer"}` 的档 ③ 名）⇒ ⇒ **实例名**来自
`ch_module` 的第一个参数 ⇒ ⇒ ⇒ 两者都会出现在外部评审看到的 RTL 里 ⇒ ⇒ ⇒
**两个不同组件给了同一个 module 名 ⇒ 产物里就撞名** ⇒ ⇒ ⇒ 所以「给名」是你自己的责任。

### D7 —— 顶层只留真正对外的接口

⚠️ **bundle 不能当顶层 IO**（bundle 成员**不是**端口 ⇒ Verilator / 外部 TB 看不到）
⇒ ⇒ ⇒ 顶层对外必须是独立的 `ch_in` / `ch_out` 字段。

## 2. 层级粒度：什么时候该「成层」（**ADR-061**）

⚠️ **层次化 API 已落地**（ADR-058 / 061 · `toVerilogHierarchical`）⇒ ⇒ ⇒
**默认仍是全扁平**（没人声明成层 ⇒ 产物与扁平**逐字节一致**）；
但**今天就可以按下面的判据组织代码**，需要交付某个 IP 单元时只需加一行声明。

### 2.1 默认 = **不成层**（inline）

> **组件默认不产生 Verilog module。** 它的逻辑会留在**最近的成层祖先** module 里
> ⇒ ⇒ 若该祖先就是 **RTL 顶层**（⇒ 你**没声明任何层**时必然如此）⇒ 端口**完全按今天的
> 扁平规则**出现（无驱动的 input ⇒ 顶层 input；任意 output ⇒ 顶层 output）⇒ **逐字节一致**。
> ⇒ ⇒ 若祖先是一个**你声明过的层** ⇒ 该 inline 组件的 output 只是那个 module 体内的信号
> （⇒ 不会一路上到 RTL 顶 —— 这正是「成层子树端口收缩」的来源）。

⇒ ⇒ ⇒ **小组件（mux / 编码器 / 断言器 / 前推 mux）不需要任何声明** ⇒ ⇒ ⇒
它们的逻辑会出现在父 module 体内 ⇒ ⇒ ⇒ 产物回到「人写的 RTL」的样子。

### 2.2 什么时候该**显式声明成层**

| 判据 | 说明 |
|---|---|
| **它是可复用的 IP 单元** | 下游要**单独**拿它的 RTL 去复用 / 交付 / 单独综合 |
| **它有自己的接口边界** | 有一组明确的 `ch_in`/`ch_out`，对外只暴露这些 |
| **你想在这一级看 RTL** | 调试波形 / 交接外部综合 / 做这一级的时序收敛 |
| **它足够大** | 一个小 mux 不值得一层；一个 5 级流水线值得 |

⇒ ⇒ ⇒ **判据是领域知识 ⇒ ⇒ ⇒ 框架不替你猜**（ADR-061 明确否决「按端口数自动推断」）。

### 2.3 声明长什么样（**已落地**形态）

```cpp
// ① 类级：组件作者声明「我是一个层」—— MUST 给名字（声明 + 命名一体）
class Rv32iPipeline : public ch::Component {
    CH_HIERARCHY_LAYER("rv32i_pipeline");   // ← 成层，module 名 = "rv32i_pipeline"
    ...
};

// ② 实例级 · 档 ②：T 已类级声明成层 ⇒ 继承 T 的类级名（单参形态）
ch::ch_layer<Rv32iPipeline> s{"s"};        // module 名 = "rv32i_pipeline"

// ③ 实例级 · 档 ③：T **未**声明（helper 被提升）⇒ MUST 在实例处给名（双参形态）
ch::ch_layer<Helper> h{"h", "helper_layer"}; // module 名 = "helper_layer"

// ④ 实例级：显式 inline（覆盖类级声明）
ch::ch_inline<Rv32iPipeline> t{"t"};
```

⚠️ `CH_HIERARCHY_LAYER` **必须带名字**（括号里给一个**字符串字面量**）⇒ ⇒
**不带名字的写法编译不过** ⇒ ⇒ 「成层却忘了命名」**在编译期就不可表达** ⇒ ⇒
不存在「运行期才发现名字不对」这回事。
⚠️ 档 ② 与档 ③ 的**重载是编译期分派的**（靠 `T` 有没有类级名）⇒ ⇒ 写错形态**编译不过**。

⚠️ **成层判定与装配点解耦** ⇒ ⇒ ⇒ 即使你的装配点**没有 active parent**
（例如下游那种「在 `setup()` 里 `make_unique` + `build(ctx)`」的写法），
组件仍能按声明成层 ⇒ ⇒ ⇒ **但前提是组件树正确** ⇒ ⇒ ⇒ 那正是 **ADR-059** 要修的东西。

### 2.4 你会付什么代价

| 代价 | 说明 |
|---|---|
| **多一层端口映射** | 子模块的端口要在父层连线 ⇒ 父层的代码比扁平**多几行** |
| **可能产生隐式端口** | 若你用 bundle 成员跨层 / 父层直接改子层 `reg->next` ⇒ ⇒ 产物里会出现 `__if_payload` / `__x_3` 这类**框架术语**的端口 ⇒ ⇒ ⇒ 建议按 §1 的 D1/D5 改成端口式 |
| **命名变长** | 模块内信号名带**完整路径前缀**（`top_p_c_r`）⇒ ⇒ 这是为了「顶层端口名与扁平逐字一致」而**故意**保留的 |

### 2.5 ⭐ 一条极重要的好消息

> **默认（谁都不声明成层）时，层次化产物与今天的扁平产物「逐字节一致」。**

⇒ ⇒ ⇒ 意味着：**你可以先写代码、零风险**，等将来需要交付某个 IP 单元时，
**再加一行 `CH_HIERARCHY_LAYER("name")`** ⇒ ⇒ ⇒ 现有 golden / perf 基线 / 外部交付物
**全部不受影响**（实测：全 inline 时层次化产物与扁平产物 `cmp` 退出码 **0**）。

## 3. 层次化下的三种写法风格（**已落地**）

⚠️ 本章三种写法**今天都可用**（`toVerilogHierarchical` 已落地）⇒ ⇒ ⇒
但**默认仍是扁平**（没人声明成层 ⇒ 产物与扁平逐字节一致）⇒ ⇒ ⇒
写法选择**只影响你想要层次化产物时**的效果。

### 风格 A —— 纯端口式（**推荐**）

```cpp
class Leaf : public ch::Component {
    __io(ch_in<ch_uint<8>> a; ch_out<ch_uint<8>> y;)
    void describe() override { io().y <<= io().a; }
};
class Mid : public ch::Component {
    __io(ch_in<ch_uint<8>> in; ch_out<ch_uint<8>> out;)
    void describe() override {
        ch::ch_module<Leaf> lf{"lf"};
        lf.io().a <<= io().in;
        io().out <<= lf.io().y;
    }
};
```
⇒ 产出的 RTL：

```systemverilog
module leaf (input logic [7:0] a, output logic [7:0] y);
    assign y = a;
endmodule
module mid (input logic [7:0] in, output logic [7:0] out);
    logic [7:0] u_lf_y;
    leaf u_lf (.a(in), .y(u_lf_y));
    assign out = u_lf_y;
endmodule
```
⇒ **零隐式端口、零冒泡端口** ⇒ ⇒ ⇒ 外部评审一眼看懂。

### 风格 B —— bundle 成员跨层（**合法但要付代价**）

```cpp
consumer.instance().stream_in <<= producer.instance().stream_out;
```
⇒ ⇒ 层次化时合成隐式端口（`__if_payload` 之类）⇒ ⇒ ⇒ **端口名带框架术语**。

### 风格 C —— 父层寄存器屏障（**跨层时序对齐**）

```cpp
exmem_alu_result <<= select(exmem_en, ex_stage.io().alu_result, exmem_alu_result);
mem_stage.io().alu_result <<= exmem_alu_result;
```
⇒ ⇒ 这是**父层内部**的连线 ⇒ ⇒ 层次化后仍然在父 module 内部 ⇒ ⇒ ⇒ **零隐式端口** ✔

## 4. 用户视角的方案审查（**本文的主要产出**）

> 判据：**一个不懂本仓实现的人**，照着 §1 写完组件树后，
> 能否**预测**层次化产物长什么样？能否**解释**产物里的每个端口名？
> 能否**判断**自己的设计是否"层次友好"？

| # | 症状（用户会看到的） | 用户会怎么反应 | 建议 | 是否需改 ADR |
|---|---|---|---|---|
| **P1** | 产物里出现 `__if_payload` / `__x_3`（**非顶层** module 内） | "这些 `__` 开头的线是什么？谁接的？" | ① MUST 随产物产出**端口清单**（名字 + 方向 + 宽度 + **来源**：哪个实例的哪个成员）；② **合成**隐式端口的前缀应可配（默认 `__`，可改成 `if_`/`x_`）⇒ ⇒ ⚠️ 冒泡端口**不在**此列（它 MUST 用 ctx 级全局名 ⇒ 与扁平产物逐字相同） | ADR-060 §2.1 增补「前缀可配」 |
| **P2** | 层次化后**顶层端口比扁平少**（无人消费的子输出不再被抬到顶层） | "我的 `dbg_xxx` 输出怎么没了？" | MUST 在文档与**端口清单**里显式标注「该输出被层次化消解（扁平下会被抬到顶层）」⇒ ⇒ 澄清是**设计意图**而非丢失 | ADR-058 §2.2 增补说明 |
| **P3** | 用户**无法控制** module 名 | "两个不同模块同名怎么办？" | ✅ **已解决**（2026-11-04 · ADR-059 D4 v2.3 / ADR-061 决策①）：**「成层声明」与「模块命名」已合并为单个宏** `CH_HIERARCHY_LAYER("name")`（声明 + 命名**一体**）⇒ ⇒ 旧的「模块命名」宏**不再单独存在**（**编译不过**）⇒ ⇒ module 名 = **你给的字符串** ⇒ ⇒ 撞名由 ADR-060 §2.6 的「同名不同类型 MUST `CHFATAL_EXCEPTION`」兜底 ⇒ ⇒ ⚠️ **代价**：module 名**不再**默认取类型名 ⇒ ⇒ 名字语义由你负责 | 无需改（已覆盖 · ADR-059 D4 v2.3） |
| **P4** | `child.io().out <<= 父层表达式` 这种**极自然**的写法，层次化需要**图重写**（把驱动搬进子模块） | "为什么我要改代码风格？" | ⚠️ **proposed API MUST 支持这种写法**（ADR-060 §2.1 第三行已列）⇒ ⇒ 且 MUST 有用例 ⇒ ⇒ 否则用户会被迫把表达式搬进子模块内部 ⇒ ⇒ ⇒ 违背"层次化不该改变用户写法" | 已覆盖（ADR-060 §2.1 第三行 + §5 效果判据） |
| **P5** | 同类型多实例**不复用** module（每实例一份） | "两个一模一样的模块为什么生成两份文件？" | 文档 MUST 写清**原因**：端口名含实例路径 ⇒ 端口签名恒不同 ⇒ 复用不触发（⇒ 换来的好处是**命名一致 + 顶层端口名与扁平逐字相同**）⇒ ⇒ **不提供** `--dedupe` 开关（⇒ 复用与命名契约不可兼得，取契约） | 已裁决（ADR-060 §5 · ADR-062 §2.6）—— 本条从「待补」变为「已定」 |
| **P6** | ⚠️ **用户无法知道自己的设计是否"层次友好"** | "我要怎么知道会不会冒出一堆隐式端口 / 悬空输入？" | ⭐ 「**层次友好度诊断** API」（形态照搬仓内已有的 `ch::core::diagnose_drive` —— 同一个枚举、单一判定实现）：报告 **隐式端口数 / 悬空输入数 / 未消费子输出数 / 跨模块 mem 访问数** ⇒ ⇒ 用户在**写代码时**就能收到 | ✅ **已裁决独立立项**（2026-11-05 · 台账 §11.1 **A4**）⇒ ⇒ **归位条件已达成**（T3-④ 已归档）⇒ ⇒ **待 planner 立项**（形态约束 = 台账 §11.2） |
| **P7** | ~~层次化产物**不被** Verilator backend 消费~~ ⇒ ⇒ 用户**不能**直接对自己的设计跑双后端 | "那我什么时候能用上？" | ✅ **已收口**（2026-11-06 · T3-005 归档）：backend **已可**消费层次化产物 ⇒ ⇒ 入口 = `try_initialize_with_verilog(verilog_path, ports, data_map)`（**只增不改** · 既有路径**逐字节不变**）⇒ ⇒ `ports` MUST 由 **emitter 产物派生**（`ch::backend_port_set(emitted, root_module)`）⇒ ⇒ **失败是致命的**（返回 `VerilatorError`，MUST NOT best-effort 静默）⇒ ⇒ ⚠️ **判别力边界**：逐拍一致性判据比较的是**两份 Verilog 产物**（同源 ⇒ 共享发射底座 ⇒ 底座算错 ⇒ 两边一起错 ⇒ 照样全绿）⇒ ⇒ 后者仍归**既有** parity + 手推期望值义务 | 无需改（ADR-058 §2.3 · **已落地**） |
| **P8** | 等价性验证是**框架自测** ⇒ 用户自己的设计**得不到**"层次化后还对不对"的反馈 | "我的设计层次化后行为变了吗？" | ⭐ 等价性 harness **做成公共 helper**（用户可在自己的 `TEST_CASE` 里调用，逐拍比对扁平 vs 层次）⇒ ⇒ ⇒ 否则「等价性」只是框架自证 | ✅ **已裁决独立立项**（2026-11-05 · 台账 §11.1 **A4**）⇒ ⇒ **归位条件已达成**（T3-005 已归档 · harness 已落地）⇒ ⇒ **待 planner 立项**（形态约束 = 台账 §11.2）⇒ ⇒ ⚠️ **语料级覆盖缺口**（层次化路径在既有语料上零覆盖）**独立立项** ⇒ ⇒ **MUST NOT 并入 P8** |
| **P9** | 跨模块 `ch_mem` 被**响亮拒绝** | "为什么我的 `child.mem.aread()` 不行了？" | ⚠️ 错误信息 MUST **直接给出两条替代路径**（"mem 与使用者同层"）⇒ ⇒ ⇒ 光报错不给出路 = 难用 | 已覆盖（ADR-060 §2.1 + 替代路径） |
| **P10** | 归属修复会**改既有 Verilog 的信号名** | "我的 golden 文件变了" | MUST 在 ①a/①b 的 change 里发布**文本变化清单**（≥ 4 处实测依赖已在 ADR-059 §5 列出）⇒ ⇒ ⇒ 用户据此更新自己的基线 | 已覆盖（ADR-059 §5） |

### 4.1 审查结论（**给方案的一句话**）

> 方案的**语义**（模块边界 = 所有权边界 · 与扁平等价 · 端口策略）是**自洽且可实现的**；
> 方案的**用户面**有 **2 个真空缺**：
> **P6（用户看不到自己的设计是否层次友好）** 与 **P8（用户拿不到"层次化后行为不变"的反馈）**
> ⇒ ⇒ ⇒ 这两条**不是**实现细节，而是**产品缺口** ⇒ ⇒ ⇒
> **建议在 P3/P4 落地前，先把这两条补进路径图**（成本低、收益直接）。
>
> **2026-11-06 更新**：方案**已落地**（T3-①a ~ T3-⑤ 全部归档）⇒ ⇒ 两条真空缺
> **已裁决独立立项**（台账 §11.1 A4）⇒ ⇒ **归位条件均已达成** ⇒ ⇒ **待 planner 立项**。
